## 0. TL;DR

- **Transport:** one WebSocket at `GET /ws?orchestrationProtocol=2&wsTicket=…`. It speaks **Effect RPC** (`effect/rpc`) with JSON serialization, not the v1 hand-rolled `{id, body}` and `push` envelope. The whole API is one `RpcGroup` (`WsRpcGroup`, `RPC:1917`). Streams are RPC methods with `stream: true`. There are no push channels anymore.
- **Auth:** you exchange a bootstrap credential (a desktop bootstrap token or a one-time pairing token) at `POST /oauth/token` for a bearer token. Then you mint a single-use RPC ticket at `POST /api/auth/websocket-ticket/rpc` and put it in `?wsTicket=`. The v1 `--auth-token` flag and `?token=` param are gone.
- **Read side:** `orchestration.subscribeShell` (the sidebar: projects plus thread rows) and `orchestration.subscribeThread` (one thread: snapshot, then a stream of domain events). Both use snapshot-plus-`afterSequence` cursors. There is no single global read model like v1's `getSnapshot`.
- **Command side:** `orchestration.dispatchCommand` takes `OrchestrationV2Command` (about 50 variants) and returns `{ sequence }`. It is idempotent per `commandId`. `orchestration.launchThread` does create-plus-workspace-plus-first-message in one call. Projects moved out of orchestration into `projects.mutate`.
- **Recommendation:** run the TUI on `@t3tools/client-runtime`, the same way `apps/mobile` does (Effect layers, `effect/reactivity` Atoms, `@effect/atom-react` hooks inside OpenTUI React). Delete most of `packages/client-core`. Start the server in `desktop` mode with a bootstrap envelope on stdin (`--bootstrap-fd 0`). Port order is in §8.

Token exchange body (`AuthTokenExchangeRequest`, `auth.ts:219`):

```
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<bootstrap credential>
subject_token_type=urn:t3:params:oauth:token-type:environment-bootstrap
requested_token_type=urn:ietf:params:oauth:token-type:access_token
[scope=<space-separated scopes>] [client_label=…] [client_device_type=desktop|mobile|tablet|bot|unknown] [client_os=…]
```

Scopes (`auth.ts:30-66`): `orchestration:read`, `orchestration:operate`, `settings:write`, `providers:manage`, `environment:maintain`, `preview:operate`, `diagnostics:read`, `terminal:read`, `terminal:operate`, `source-control:write`, `filesystem:read`, `filesystem:write`, `access:read`, `access:write`, `relay:read`, `relay:write`.

How the WS upgrade authenticates (`apps/server/src/auth/EnvironmentAuth.ts:1241-1296`):

1. If `?wsTicket=` is present, the server verifies it. The ticket's audience must match `"rpc"`. If the session is DPoP-bound, it also needs a proof in the `dpop` header or the `?dpop=` query param. Param names come from `EnvironmentAuth.ts:587-588`.
2. Otherwise it falls back to `authenticateRequest`, which checks the session cookie, then `Authorization: Bearer …`, then the legacy cookie (`EnvironmentAuth.ts:634-680`). Cookie credentials are origin-checked. **A Node or Bun client using the `ws` package could send `Authorization: Bearer` on the upgrade and skip the ticket.** Upstream clients always use tickets because browsers and React Native can't set upgrade headers.

What the client builds: `resolveRemoteWebSocketConnectionUrl` (`CR/authorization/remote.ts:275`). It mints an `rpc` ticket, sets the path to `/ws`, adds `wsTicket`, and appends client metadata params (`clientSurface`, `clientAppVersion`, `clientDeviceType`, `clientOs`; `remote.ts:62`). The `orchestrationProtocol` param is added in `CR/connection/compatibility.ts:39`. `ClientSurface` already includes `"cli"` (`packages/contracts/src/baseSchemas.ts:279`).

Server auth policy (`apps/server/src/auth/EnvironmentAuthPolicy.ts:20-40`):

- `mode=desktop` on loopback gives policy `desktop-managed-local`, bootstrap method `desktop-bootstrap` only.
- `mode=desktop` on a reachable host gives `desktop-bootstrap` plus `one-time-token`.
- `mode=web` gives `one-time-token` only (policy `loopback-browser` or `remote-reachable`).

### 2.2 Stream and cursor semantics

**Shell stream** (`subscribeOrchestrationV2Shell`, `apps/server/src/ws.ts:991`):

- The first item is `{kind:"snapshot", snapshot: OrchestrationV2ShellSnapshot}`. The snapshot is `{schemaVersion, snapshotSequence, projects: OrchestrationProjectShell[], threads, archivedThreads, olderSettled?}` (`OV2:2066-2079`).
- With `requestCompletionMarker`, a `{kind:"synchronized"}` follows.
- Then incremental items: `project.updated` / `project.removed` and `thread.updated` / `thread.removed` (each with `location: "active"|"archive"`). Each carries a `sequence`.
- **The shell stream gives you whole thread rows, not events.** You replace the row by id. Client logic lives in `CR/state/shell.ts` (`makeEnvironmentShellState`) and `CR/state/shellReducer.ts` (`applyShellStreamEvent`).
- The client ignores items whose `sequence` is at or below the current `snapshotSequence`.

**Thread stream** (`subscribeOrchestrationV2Thread`, `ws.ts:786-990`):

- Without `afterSequence`, you get `{kind:"snapshot", snapshotSequence, projection, historyCursor?, hasMoreHistory?, …}`, then an optional `synchronized`, then live `{kind:"event", sequence, event: OrchestrationV2DomainEvent}`.
- With `afterSequence`, the server replays stored events through its high-water mark. It falls back to a fresh snapshot when replay would exceed limits or the thread was recreated, then goes live. The client must dedupe overlap by `sequence`, because the server subscribes before it reads.
- Unknown event types decode to `{kind:"unknown-event", sequence, eventType}`. They still advance the cursor (`OV2:3609-3640`).
- The `accept*` flags are opt-in wire optimizations: bounded snapshot windows, deduped bodies, compact id tables via `withRecordIdTable` (`packages/contracts/src/orchestrationV2IdTable.ts`). If you set them, you must reconstruct the full data with client-runtime helpers (for example, `boundedSnapshotProjection`). Only send them to servers whose `ServerConfig` advertises the matching capability: `threadSnapshotPagination`, `threadResumeCompletionMarker`, and so on (`packages/contracts/src/server.ts:596-614`).
- The client-side reducer that applies domain events to a projection is `applyOrchestrationV2ProjectionEvent` (`CR/state/orchestrationV2Projection.ts:259`). The per-environment thread state machine is `CR/state/threads.ts` (`makeEnvironmentThreadState`, `createEnvironmentThreadStateAtoms`).

**Domain events** (`OrchestrationV2DomainEvent`, `OV2:1720-1865`). Every event has the base fields `{id, threadId, runId?, nodeId?, driver?, providerInstanceId?, rawEventId?, occurredAt}` (`OV2:1709`). Each event's payload is the **whole updated entity**, so the reducer is upsert-by-id:

- `thread.created` and about 20 `thread.*` lifecycle types (archived, unarchived, deleted, settled, …, `thread.provider-switched`, `thread.metadata-updated`), each with payload `AppThread`
- `thread.pull-request-link-updated`
- `run.created`, `run.updated`, `run.background-work-cancelled`
- `run-attempt.created`, `run-attempt.updated`
- `node.updated`, `subagent.updated`
- `provider-session.detached`, `provider-thread.updated`, `provider-turn.updated`
- `runtime-request.updated`, `message.updated`, `turn-item.updated`, `plan.updated`
- `checkpoint-scope.created`, `checkpoint.captured`, `checkpoint.rollback-requested`
- `context-handoff.updated`, `context-transfer.created`, `context-transfer.updated`

## 3. Orchestration v2 command side

### 3.1 Dispatch and receipts

- `orchestration.dispatchCommand(OrchestrationV2Command) -> {sequence: NonNegativeInt}` (`OV2:2753`, `OV2:3423`). Errors: `OrchestrationV2DispatchCommandError {commandId, commandType, message, detail?}` (`OV2:3668`).

- Every command carries a client-generated `commandId` (UUID). See `allocateCommandId` in `CR/operations/commands.ts:265`.
- `OrchestrationV2InternalCommand` (`OV2:3218-3313`) is server-only and rejected by `dispatchCommand`.

- `t3 auth session issue --base-dir … [--scopes …] --token-only` mints a scoped **bearer token directly**, without running the server (`apps/server/src/cli/auth.ts:159`).
- `t3 auth pairing create` issues a one-time pairing token.

**One server per base dir.** The server takes an ownership lock and exits with code **78** (`SERVER_EXIT_CODE_STATE_DIR_OWNED`, `packages/contracts/src/desktopBootstrap.ts:6`) if another server owns the directory. A running server records `{pid, host, port, origin, serverVersion, …}` in `<state>/server-runtime.json` (`apps/server/src/serverRuntimeState.ts:12`, `apps/server/src/config.ts:170`). A TUI that shares `~/.t3` with desktop or `t3 service` has to attach to the existing server instead of spawning a second one.

### 5.2 How desktop launches and authenticates

From `apps/desktop/src/backend/DesktopBackendConfiguration.ts:490-545`:

- Desktop spawns `process.execPath [--require cache] <backendEntry> --bootstrap-fd 3` with `ELECTRON_RUN_AS_NODE=1`, and writes the envelope to fd 3.
- WSL launches use `--bootstrap-fd 0`, so the envelope goes over stdin (`DesktopBackendConfiguration.ts:~707`).
- Envelope schema `DesktopBackendBootstrap` (`packages/contracts/src/desktopBootstrap.ts:8`): `{mode:"desktop", noBrowser, port, t3Home?, host, desktopBootstrapToken, desktopBootstrapSecret?, shellEnvironmentPrepared?, tailscaleServeEnabled, tailscaleServePort, otlp*?, desktopTelemetryFd?, desktopBrowserFd?, …}`. Envelope values sit below CLI flags and env in precedence (`resolveServerConfig`).
- Readiness: desktop polls `GET /.well-known/t3/environment` (`apps/desktop/src/backend/DesktopBackendManager.ts:43`).
- Bearer: `DesktopLocalEnvironmentAuth` derives the credential. When a secret is configured, it computes `currentDesktopBootstrapToken(secret, now)`, an HMAC over a 12-hour window (`packages/shared/src/desktopBootstrapToken.ts`). Otherwise it uses the static `desktopBootstrapToken`. It exchanges the credential at `/oauth/token` with `bootstrapRemoteBearerSession` and caches `access_token`.

### 5.3 What a TUI should copy

1. **Attach first.** Read `<base>/userdata/server-runtime.json`. If the pid is alive and the version is compatible, connect to its `origin`. To get credentials for an existing server, run `t3 auth session issue --token-only --base-dir <base>` (offline mint), or ask the user to pair.
2. **Otherwise spawn** `node <server>/bin.mjs [cwd] --bootstrap-fd 0` and write a `DesktopBackendBootstrap` JSON to the child's stdin. Use `mode:"desktop"`, `noBrowser:true`, `host:"127.0.0.1"`, a free `port`, a random `desktopBootstrapToken` (or a `desktopBootstrapSecret`), and `tailscaleServeEnabled:false`. Poll `/.well-known/t3/environment`, then exchange the token at `/oauth/token`. stdin is the fd that works most simply under Bun; fd 3 needs `node:child_process` `stdio:[…,'pipe']` support. Desktop mode skips `--auto-bootstrap-project-from-cwd`, so create the project for cwd through `projects.mutate`, or pass the flag explicitly.
3. **Map the session through `PrimaryEnvironmentAuth`.** Provide `ClientCapabilities.PrimaryEnvironmentAuth { bearerToken }` with that token, and register a `PrimaryConnectionTarget{httpBaseUrl, wsBaseUrl}` through `PlatformConnectionSource`. That is what web does inside Electron (`apps/web/src/connection/platform.ts:325-440`).

## 7. Gotchas

- `TurnId`, `ApprovalRequestId` and `ProviderKind` are gone from the client surface. Everything keys on `ThreadId`, `RunId`, `NodeId`, `TurnItemId`, `RuntimeRequestId`, `MessageId`, `CheckpointId`, `ProviderInstanceId`.
- Capability-gate opt-in inputs: check `ServerConfig` flags (`shellThreadFamilies`, `shellOlderSettled`, `threadSnapshotPagination`, `threadResumeCompletionMarker`, `environment.capabilities.serverResolvedCommandContext`, …) before sending the matching fields. The server rejects or ignores unknown keys depending on the schema.
- Forward compatibility: turn-item and event unions use `ForwardCompatibleUnion`, so unknown variants are dropped while the cursor still advances. Reuse the contracts codecs instead of hand-decoding.
- `creationSource` is `"web" | "mobile" | "mcp" | "provider" | "server"` (`OV2:89`). There is no `"cli"` or `"tui"` value. The TUI must send `"web"` or upstream has to add a literal. (`ClientSurface` already has `"cli"` for connection metadata.)
- `projects.list/add/remove` still appear in `WS_METHODS`, but calling them fails because they aren't in the RPC group.

## 8. Recommendation: how to build the TUI on upstream

**Architecture.** Treat the TUI as a third `client-runtime` consumer next to web and mobile. Don't keep a parallel `packages/client-core`.

1. **Runtime layer** (like `apps/mobile/src/lib/runtime.ts`). Provide `Socket.layerWebSocketConstructorGlobal` (Bun has a global `WebSocket`), `layerRemoteHttpClient(fetch)` from `@t3tools/client-runtime/rpc`, and a file-backed persistence layer: SQLite via `bun:sqlite`, or JSON under `~/.t3/tui`. Persistence implements `Persistence.ConnectionTargetStore`, `ConnectionRegistrationStore` and `EnvironmentCacheStore`.
2. **Platform layer** (like `apps/mobile/src/connection/platform.ts`, but much smaller):
   - `Connectivity` (always `online`) and `Wakeups` (`Stream.empty` or SIGCONT).
   - `ClientCapabilities.ClientPresentation` with `{label:"T1 Code", deviceType:"desktop", surface:"cli"}`.
   - `ClientCapabilities.PrimaryEnvironmentAuth` returning the bearer from §5.3.
   - `PlatformConnectionSource` emitting one `PrimaryConnectionRegistration(PrimaryConnectionTarget{httpBaseUrl, wsBaseUrl})`.
   - Stub `SshEnvironmentGateway`, `CloudSession` and `RelayDeviceIdentity` to fail or return none until those features are wanted.
3. **Connection runtime** (copy `apps/mobile/src/connection/runtime.ts`). `Connection.layerWithOptions(...)` plus `ShellSnapshotLoader`, `BoundedThreadSnapshotLoader` and `ThreadHistoryController`, wrapped in an `Atom.AtomRuntime`.
4. **State.** Consume `@t3tools/client-runtime/state/shell` (sidebar), `state/threads` (thread detail and history paging), `state/server` (config, providers, keybindings), `state/terminal`, `state/vcs`, `state/models`, `state/thread-requests`, `state/thread-subagents`, `state/turn-item-presentation`, and `work-log/*`.
5. **Commands.** Use `@t3tools/client-runtime/operations` (`startThreadTurn`, `interruptThreadTurn`, `respondToThreadApproval`, `forkThreadFromRun`, …) instead of hand-building commands.
6. **UI binding.** `@effect/atom-react` hooks work in any React 19 renderer, OpenTUI included. Keep OpenTUI components and swap their data source. Check that `@effect/atom-react` doesn't pull DOM-only APIs into Bun; a quick spike settles that.
7. **Server launch.** A small `ServerLauncher` module that attaches or spawns per §5.3, replacing the fork's `--auth-token` launch.

**Port order.** Each step should end with the TUI runnable.

1. **Contracts and deps.** Rebase, delete v1 contract imports, and add `@t3tools/client-runtime` and `@effect/atom-react` to `apps/tui`. Get `bun typecheck` compiling with the TUI's data layer stubbed.
2. **Launch and auth.** Implement the server launcher (attach or spawn, bootstrap envelope on stdin, `/oauth/token` exchange) plus the runtime and platform layers. Verify with `server.getConfig` over the session.
3. **Shell (sidebar).** Bind `subscribeShell` through `state/shell`: projects, thread rows, status, pending-request badges. Replace the v1 `getSnapshot` / `domainEvent` read model.
4. **Thread view, read-only.** Bind `subscribeThread` through `state/threads` and render `visibleTurnItems` with `turnItemPresentation` and `work-log/*`: messages, reasoning, tool rows, plans, errors. Add history paging.
5. **Composer and run control.** `launchThread` for new threads, `message.dispatch` via `startThreadTurn` (auto, queue, steer), `run.interrupt`, model and runtime-mode pickers (`thread.model-selection.set` / `provider.switch`, `thread.runtime-mode.set`), with the provider list from `ServerConfig.providers`.
6. **Approvals and questions.** `runtime-request.respond`, `thread.user-input.dismiss`, using `state/thread-requests`.
7. **Thread management.** Rename, archive, delete, settle and pin; project create and delete via `projects.mutate`; file search (`projects.searchEntries`) for `@` mentions; open-in-editor.
8. **Terminals, diffs, git.** `terminal.*` streams (the Rex tabs and panes from fork commit `e7805f09e6`), `getTurnDiff` / `getFullThreadDiff` and `review.*` for the diff pane, `subscribeVcsStatus` and `vcs.*` for branch and worktree.
9. **v2-only features.** Queue editing, fork and merge-back, subagent tree (`getThreadFamily`), checkpoint rollback, keybinding sync (`server.upsertKeybinding`), diagnostics.
10. **Delete `packages/client-core`.** Keep only TUI-specific helpers (for example `contextWindow`, if upstream has no equivalent) and move them into `apps/tui`.
